# xr3-sky Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an `xr3-sky` CLI that launches committed r3 jobs as SkyPilot managed jobs. It
moves job files, dependency outputs and results between the laptop r3 repo and Ceph S3, and
pulls outputs back.

**Architecture:** This mirrors `xr3-slurm`.
- A thin click CLI (`extensions/xr3-sky/xr3-sky`) does the I/O.
- Two pure, unit-tested modules hold the logic:
  - `xr3skylib.py`: naming, S3 key layout, `sky.yaml` merge and validation, done-state
    decisions, and task rendering.
  - `xr3skys3.py`: an object-store protocol with a boto3 implementation and an in-memory
    fake for tests.
- The pod-side work is a bash bootstrap script (`xr3sky_bootstrap.sh`) inlined into the
  task's `run:`. Its S3 command is injectable, so it can be tested locally against a
  directory-backed fake `aws`.

**Tech Stack:** Python 3.12 (toolchain venv), click, pyyaml, boto3 (new dependency), r3,
SkyPilot 0.13 CLI (`sky jobs launch/queue/logs/cancel`), bash, AWS CLI inside the pod.

**Spec:** `docs/specs/2026-11-23-xr3-sky-design.md` (sections are cited as §N below). The
foreman part of the spec (§5.7) has its own plan:
`docs/superpowers/plans/2026-11-23-foreman-skypilot-backend.md`.

## Global Constraints

- Code lives in `extensions/xr3-sky/`. Config lives in the `sky:` section of `~/.config/xr3.yaml`, loaded through `extensions/xr3/xr3config.py`.
- The pure modules use only the stdlib and pyyaml, so the tests run with `uv run --with pytest --with pyyaml pytest extensions/xr3-sky/tests -q`.
- S3 settings:
  - Endpoint: `https://rgw-cold.enigmatic.stanford.edu`.
  - Addressing style `path`, region `stanford`.
  - In-pod internal endpoint: `http://rgw-cold.rook-ceph.svc` (§5.5). It is used only when it resolves; otherwise the pod falls back to the public endpoint. The builder must confirm the scheme and port during Task 10.
- Default config values (§5.9): `bucket: federico-r3`, `prefix: r3`, `aws_profile: enigma`, `sync_interval: 300`, `pull_max_size: 100MB`, `push_confirm_above: 5GB`, `secrets: [WANDB_API_KEY]`, `defaults.resources: {cpus: 4, memory: 16}`.
- Managed-job name: `<user>-r3-<first 8 chars of job id>` (§5.3). `<user>` is the config value `sky.user`, defaulting to the local part of `$SKYPILOT_USER`. Submission is always `sky jobs launch`, never `sky launch` (DO policy).
- HAMi `gpumem` table in MiB, as one-slot / whole-card values:

  | Accelerator | One slot | Whole card |
  |---|---|---|
  | `RTXPRO6000` | 9788 | 97887 |
  | `H100-80GB` | 8155 | 81559 |
  | `L40S` | 4606 | 46068 |

  Every other accelerator is non-HAMi.
- Priority classes allowed: `low`, `medium`, `high`. `high` requires `--allow-high`. `critical-infra` and retired classes are always refused.
- Secrets are passed only as `--secret NAME`, with values taken from the laptop environment or the AWS profile. They are never written to a file, an S3 object or the rendered task YAML.
- Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A pod is preempted mid-run.** The managed job recovers, bootstrap pre-populates `output/` from S3, and the job resumes rather than restarting from zero. Tested in Task 5 (`test_bootstrap_resumes_partial_output`).
2. **`run_inner.sh` fails.**
   - `output/done` becomes `failed` in S3.
   - `output.complete` is not written.
   - The exit status propagates, so SkyPilot shows `FAILED`.
   - Tested in Task 5 (`test_bootstrap_failure_marks_failed`).
3. **A job is relaunched after a failure, without and then with `--restart-failed`.** Without the flag it is skipped. With it, the S3 marker becomes `restart` before submission. Tested in Task 3 (`test_launch_decision_*`) and Task 7 (`test_launch_restart_failed_rewrites_s3_marker`).
4. **A dependency job has no output anywhere** (neither local nor in S3). This is a clear error that names the dependency, and nothing is submitted. Tested in Task 4 (`test_plan_push_missing_dep_output_errors`).
5. **A user runs `launch` off the VPN.** Preflight fails before any upload, with "connect to the Stanford VPN". Tested in Task 7 (`test_preflight_s3_unreachable_message`).

### Task 2: `sky.yaml` merge and validation

**Files:**
- Modify: `extensions/xr3-sky/xr3skylib.py`
- Test: `extensions/xr3-sky/tests/test_xr3skylib.py`

**Interfaces — Produces:**
- `class SkySpecError(ValueError)`.
- `HAMI_GPUMEM: dict[str, tuple[int, int]]`. Values are copied from Global Constraints.
- `merge_task(defaults: dict, job_fragment: dict) -> dict`: a deep merge where the job wins.
  - It raises `SkySpecError` if the fragment contains a key outside `{"resources", "config", "envs", "secrets", "num_nodes"}`.
- `validate_and_fill(task: dict, *, whole_card: bool, allow_high: bool, infra_override: Optional[str]) -> dict`: returns a new task dict with the `gpumem` filled in, or raises `SkySpecError` with one of the messages below.
- Helpers `accelerator_of(task) -> Optional[str]` and `gpumem_of(task) -> Optional[int]`. Each reads `config.kubernetes.pod_config.spec.containers[0].resources.limits["nvidia.com/gpumem"]`.

**Rules** (§5.2 placement rule). Each message must contain the quoted fragment:

| Condition | Result |
|---|---|
| `config` key under `resources` | `"config: must be top-level"` |
| `num_nodes` other than 1 | `"num_nodes must be 1"` |
| `resources.accelerators` is a list or set, or `resources.any_of` / `ordered` with a GPU | `"GPU jobs must pin exactly one accelerator"` |
| HAMi accelerator, no gpumem, `whole_card=False` | `"needs a nvidia.com/gpumem cap"`; the message names both table values |
| HAMi accelerator, `whole_card=True` | fill in the whole-card value |
| gpumem above the whole-card value | `"exceeds"` |
| `priorityClassName` not in `low`/`medium`/`high` | `"priority class"` |
| `high` without `allow_high` | `"--allow-high"` |
| any volume value starting with `do-` | `"DO has no persistent volume"` |
| `infra_override` given and the task already has a different `resources.infra` | `"--infra contradicts sky.yaml"` |
| `infra_override` given and the task has none | set `resources.infra` |

### Task 7: CLI `launch` (preflight, push, submit, `--dry`)

**Files:**
- Create: `extensions/xr3-sky/xr3-sky` (executable; same import pattern as `xr3-slurm`)
- Create: `extensions/xr3-sky/tests/test_cli_launch.py`. Uses click's `CliRunner` with a monkeypatched `MemoryStore`, a fake `sky` on `PATH` that records its argv and the task YAML, and a temporary r3 repo made with `r3 init` plus committed fixture jobs.

**Interfaces:**
- **Consumes:** everything from Tasks 1–6.
- **Produces:**
  - `cli` (click group).
  - `_store(cfg) -> Store`, which can be monkeypatched.
  - `_deps_closure(repo, job) -> tuple[list[DepInfo], list[tuple[str,str]]]`, walking `JobDependency` / `GitDependency` recursively.
  - `_preflight(store, need_sky: bool) -> None`, which raises `click.ClickException` with these messages:
    - `"S3 unreachable — connect to the Stanford VPN"`
    - `"SkyPilot API unreachable — run sky-up"` (from `sky api info` failing)
    - `"R3_REPOSITORY is not set"`

**Command:**
```
launch JOB_IDS… [-t/--tag] [-q/--query] [--dry] [--infra TEXT] [--whole-card] [--allow-high]
       [-r/--restart-failed] [--fresh] [--allow-unfinished-deps] [--yes] [-v]
```
- Job selection and de-duplication are copied from `xr3-slurm submit`.
- Steps for each job:
  1. Check that `run.sh` exists and the directory is a UUID.
  2. Resolve the done state with `effective_done`, reading the S3 marker first.
